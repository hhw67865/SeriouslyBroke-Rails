# The Cutover — Implementation Plan (Plan 3, the conversion's finish)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Every user's data lives in the envelope model, and the legacy tracking machinery that coexistence required is deleted.

**Architecture:** One data migration (§6.1, with §7a's ordering fix) creates the invariant for existing data; then the legacy half comes out in slices — seeds first (so every later slice tests against the post-cutover world), then category caps, then the dashboard's budget-vs-cap machinery, then the savings category type, then the schema tightenings that needed the backfill. **This is the only plan of the four that rewrites existing user data.** Everything else in the conversion added beside the old system; this plan is why it could.

**Tech Stack:** Rails 8.1, PostgreSQL (UUID PKs, `money` columns), RSpec, FactoryBot, Capybara.

**Spec:** `docs/superpowers/specs/2026-08-14-envelope-budgeting-design.md` (§6 blast radius, §6.1 migration, §7a "Plan 3 must")
**Inheritance list:** the bottom of `docs/superpowers/plans/2026-08-17-logging-and-tracking.md` — cutover-coupled items only; see "Out of this plan" below.

## Decisions this plan settles

### 1. The migration order is envelopes-first, and callbacks are bypassed

§7a's warning, flagged since Plan 1: `Category#destroy_budget_if_pool_linked` destroys a
category's cap the moment `pool_id` is assigned, so §6.1's written order (point categories at
the account in step 2, convert caps in step 4) **silently destroys every user's budgets** —
"the step that loses data." The migration runs **envelope creation first** (each capped
category: create the envelope, move the cap onto it as a monthly rule, re-point the category),
and every category write in the migration uses `update_all`/migration-local table classes so
no callback and no future validation can fire. The migration must not reference app models at
all — migration-local `class MigrationCategory < ActiveRecord::Base; self.table_name = ...`
throughout, so next year's model changes cannot rewrite history.

### 2. The migration verifies itself against figures computed outside the app's readers

After migrating a user, the migration asserts — with raw SQL sums, not `PoolCalculator` —
that: every category has a `pool_id`; every non-account pool has an `account_id`; the number
of envelope rules created equals the number of caps that existed; zero savings-type entries
remain; and **`Σ pools == the bank truth`**, where bank truth is `Σ income entries − Σ expense
entries` computed straight off `entries` (movements net to zero by construction, so the
invariant the app will now display is derived independently before the app ever displays it).
Any failure raises inside the transaction: a half-migrated user is impossible. The migration
is **idempotent** — a second run finds nothing to do and changes nothing, asserted.

### 3. Categories require a pool after the cutover; the nil-fallback line leaves the spec

The domain spec's §3 says a nil `categories.pool_id` "=> the user's default account" — but 2c
removed the fallback from every reader after proving nothing implemented it, and `ENTRY_POOL_ID`
resolves nil to nowhere. Post-migration the honest rule is: **`pool_id` is required on
categories** (the migration guarantees it; a validation enforces it; the category form defaults
new categories to the default account). `Category#buffer_funded?` simplifies to
`expense? && pool.pool_type_account?` — the nil arm dies with the shape. The spec's §3 line is
corrected in Task 6.

### 4. Savings-type entries convert to movements and are then deleted; their categories go too

A savings entry never crossed the app's boundary — it was always "I moved my own money" wearing
the wrong record type. Each becomes a `PoolMovement` (from the user's default account, to the
entry's category's pool, same datetime, `kind: :transfer`, `source_entry_id` nil), and the
entry row is **deleted** — keeping both would double-count the moment anything summed entries
and movements together. The savings categories (and their items) are then destroyed: they were
plumbing for the retired contribution flow, and post-cutover contributions are reallocations.
Counts are conserved and reported (N entries → N movements → 0 entries). Only then can the
enum value be removed (Task 5) — Ruby-side, integer 2 never reused.

### 5. Post-cutover, contributing to a goal is a reallocation — the entry form drops savings

The entry form handles expense and income only. Money reaches a savings goal through the fill
(a rule on the goal) or the reallocation screen — both shipped and reviewed. The impact card's
contribution arms, the category form's savings option, and every savings-type reader die in
Task 5. The card's "goal" arm survives where the *pool* is a goal (an expense category can
draw from one); the *category-type* arms do not.

### 6. Budget-vs-cap becomes funded-vs-spent, computed at the pool — or leaves the dashboard

§6's ruling: `CategoryCalculator`'s pace/percentage machinery "loses its basis." Task 4 decides
per chart, with the default being **replace with the pool-level truth where a one-reader figure
exists** (funded = the envelope's balance + period allocations; spent = the period's expense
entries in the pool's lane) **and delete where it does not** — a chart kept alive by a new
second reader would recreate the defect family three plans spent closing. Deletions are listed
in the task report; the dashboard must not render an empty husk where a chart was.

## Task 1: The migration

**Files:** create the migration + `spec/migrations/cutover_spec.rb`; no app code changes

Decisions 1, 2, 4. The steps, per user, in one transaction:

1. Ensure a default account: reuse the user's existing `pool_type: account` flagged default,
   else the first account, else create "Checking" (`pool_type: :account`), and set
   `users.default_account_id`.
2. Assign `account_id` to every account-less non-account pool (the default account).
3. **Envelopes first**: for each category-mode budget, create a budget-type pool named for the
   category (name-collision-safe: reuse an existing budget pool of that name for this user —
   the accept flow's precedent — else suffix), insert the rule (`pool_id`, same `amount`,
   `interval_months: 1`, `basis: 0` monthly, `prorated` dropped), null the budget's
   `category_id`, and `update_all` the category's `pool_id`.
4. Point every remaining nil-pool category at the default account (income and expense alike —
   income categories MUST point at an account, and the expense ones become the buffer-funded
   shape the app already renders honestly).
5. Convert savings entries per decision 4; destroy the savings categories and their items.
6. Verify per decision 2; raise on any failure.

The spec plants every legacy shape the wild can hold — a capped category, a category sharing a
name with an existing pool, an account-less savings pool, a savings category with entries and
items, an income category with entries, a user with NO data, a user already migrated (the
idempotence run) — and asserts the migration's own verification catches a sabotaged case
(delete one movement inside a test double-run and the raise fires: the verifier must be shown
able to fail). `db:seed:replant` + migrate on dev must converge; the one-task window where
replant recreates legacy shapes (until Task 2 rewrites seeds) is acknowledged in the report.

- [ ] Migration, local classes, envelopes-first, idempotent
- [ ] Verification with outside-the-readers sums; the sabotage case proves it can fail
- [ ] Migration spec green; dev migrated and verified; commit
